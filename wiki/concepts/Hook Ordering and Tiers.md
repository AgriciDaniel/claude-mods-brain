# Hook Ordering and Tiers

Hooks for one event nest in a fixed order of five tiers, outermost first: `prepend` (managed mods an admin lists first), `user` (everything a person installs), `append` (managed mods listed last), `builtin` (mods bundled in the binary), and `core` (Claude Code's own innermost link) (C-API-015; types 2.1.288 L11897-11907). Earlier means outer means more authority: an outer hook sees the event first, the result last, and can stop inner hooks from running; an inner hook cannot stop an outer one from seeing anything (docs-mods-events L285). Settings `PreToolUse` hooks sit at two fixed points in this order.

## The order, top to bottom

| Position | Who | Tier | Evidence |
|---|---|---|---|
| 0 | Managed-settings `PreToolUse` hooks (tool calls only); a block is final | outside the mod chain | docs-mods-events L300 |
| 1 | `sec-default@builtin` where it loads, then mods in managed `prependPlugins`, then other org mods not in `appendPlugins` | `prepend` | docs-mods-events L289; docs-mods-reference L268, L276 |
| 2 | Mods the user installs; a mod runs before the mods it lists under `dependencies`; within a module, `on` call order | `user` | docs-mods-events L290, L294 |
| 3 | Mods in managed `appendPlugins`, in listed order | `append` | docs-mods-events L291 |
| 4 | Other mods built into Claude Code (see the ecosystem lane's built-in mod notes) | `builtin` | docs-mods-events L292 |
| 5 | Claude Code's behavior; for `tool.call` this includes non-managed `PreToolUse` hooks, the permission check and the tool | `core` | docs-mods-events L301 |
| after | `tool.check` decides with the rules, mode and `PreToolUse` result known | its own chain | docs-mods-events L303 |

`sec-default@builtin` loads ahead of every user mod on a machine with managed settings or for a user signed in with a Team or Enterprise plan; if managed `prependPlugins` is set, it loads only when that list names it, at that position (docs-mods-reference L276). See [[Built-in sec-default Mod]].

## Who raised it: `next.origin`

`next.origin` is `{ plugin, tier }` of whoever fired the event; Claude Code is `{ plugin: 'engine', tier: 'core' }`, a `Client` post is `{ plugin: 'client', tier: <owner's> }` (types 2.1.288 L6866-6878). The host sets it from the calling environment; nothing a plugin writes reaches it, and every hook of one dispatch sees the same origin (L6158-6169). That makes it usable for policy, unlike `e.surface`, which the typings call "a rendering fact and not a trust signal" (L9064-9065).

```ts
import type { Register } from 'claude-code'

export const register: Register = (on) => {
  // Only intercept model-made tool calls, not other mods' $.tool.call
  on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
    if (next.origin.plugin !== 'engine') return next(e)
    $.ui.log('model ran: ' + e.command, { to: 'debug' })
    return next(e)
  })
}
```

## Skipping tiers: `next.to(e, tier)`

`next.to(e, tier)` continues the dispatch at a later tier, skipping every link in between (C-API-015):

- Targets (`TargetTier`): `append`, `builtin`, `core` (types 2.1.288 L11620).
- Only managed mods may call it: a `prepend` hook may name `append`, `builtin` or `core`; an `append` hook may name `core`. It never skips a tier with more authority, "so no user hook skips the org's" (types L6125-6133; docs-mods-reference L41).
- `next.to(e, 'append')` from a prepend mod skips every user-installed mod.
- Skipped links appear in `next.trace` with outcome `skipped` and reason `bypassed by <plugin>` (types L12436-12441).

```ts
// In an org mod listed in prependPlugins:
on('tool.call', { tool: /^mcp__payments__/ }, async ($, e, next) => {
  return next.origin.tier === 'prepend' ? next(e) : next.to(e, 'append') // user mods never see payment tool calls
})
```

## `$` calls and recursion

A mod's own `$.tool.call`, `$.prompt.submit`, `$.command.run`, `$.session.compact` and similar run "through every hook but the calling one" (types 2.1.288 L2664, L2738, L2812), so a mod never re-enters its own hook frame, while every other mod, outer and inner, sees the call with `next.origin.plugin` set to the caller.

## Ordering facts that bite

- A user mod that answers `tool.call` without calling `next` keeps non-managed `PreToolUse` hooks from running (docs-mods-events L301). Porting shell guards into a mod changes who sees what; see [[Mods vs Classic Hooks]].
- `PreToolUse` blocks and `deny` rules are separate cases. A `tool.check` hook can approve a call that a non-managed `PreToolUse` hook blocked (docs-mods-events L200, L303); only a block from a managed `PreToolUse` hook is final (docs-mods-admin L66).
- `deny` rules hold against a user's mod only where `sec-default` loads, and managed `allowModsToOverrideDenyRules` relaxes that (docs-mods-reference L270, docs-mods-admin L66). Neither covers `PreToolUse` blocks. Without the guard, a mod can approve a call a `deny` rule refuses (inference from docs-mods-admin L66).
- For `AbovePrompt`, a tree from an outer mod replaces what inner mods draw unless it includes `await next(e)` (docs-mods-interface L204).
- A `ui.press` or `ui.input` hook in an outer mod runs before your control's callback and can swallow it (docs-mods-interface L486).
- `plugin.register` judges are "the plugins admitted before it and the binary's" (types 2.1.288 L4161-4166): only outer mods can refuse inner ones.

## Recommendations

- Assume you are in the `user` tier with org mods outside you; never rely on seeing an event first. EVIDENCE-BASED
- Key policy on `next.origin` and `e.agentId`, never on `e.surface` or a sender name a message carries. EVIDENCE-BASED
- Use `dependencies` in the manifest when your mod must wrap another user mod. EVIDENCE-BASED
- In tests, assert ordering with `next.trace` and the testing kit's `tier` helper rather than log order. PRACTITIONER
